# Свои правила очистки (Custom\*.ini)

Папка `Custom\` рядом с `CleanSweep.exe` — место для собственных
правил клинера. Формат — обычный winapp2.ini, тот же синтаксис, что у
встроенных баз (`data\Winapp2.ini` и др.).

- Файл `Имя.ini` — включён, попадает в базу при загрузке клинера
  (приоритет выше всех остальных источников: при совпадении имён записей
  побеждает Custom).
- Файл `Имя.ini.disabled` — выключен, клинер его не читает.
  Кнопка «Вкл/выкл» в диалоге «Свои правила» просто переименовывает файл.
- Кодировка — **UTF-8** (с BOM или без — читаются обе).
- Строки, начинающиеся с `;` — комментарии.

Диалог управления: клинер → кнопка **«Правила…»**.
**«Новая запись…»** и **«Изменить…»** открывают визуальный редактор:
поля записи, списки FileKey/RegKey/ExcludeKey/детекции и кнопка
**«Проверить…»** — живой предпросмотр через тот же `Analyze`, что и
реальная чистка (удаление при этом не выполняется). Текстовый редактор
никому не мешает — ini можно править и вручную.

Править можно и прямо из списка клинера: контекстное меню записи →
**«Править запись…»**. Custom-запись открывает свой файл; запись
встроенной базы сначала копируется в `Custom\<имя>.ini` — копия
переопределяет оригинал при загрузке, сами базы не изменяются.

Массовое клонирование: списки записей поддерживают мультивыбор
(Ctrl/Shift). Кнопка **«В Custom»** (или пункт контекстного меню
**«Копировать в Custom»**) записывает каждую выбранную запись базы
в отдельный `Custom\<имя>.ini` — удобно изучать и править «эталонные»
правила. Уже существующие файлы спрашивают перезапись (есть
«Да для всех»), Custom-записи пропускаются.

В поставке лежат два прокомментированных примера на реальных целях —
`Пример 1 — кэш обновлений Windows.ini` (один FileKey с RECURSE на
`%WinDir%\SoftwareDistribution\Download`) и
`Пример 2 — журналы и дампы Windows.ini` (детекция файл/ОС, флаги,
реестр RecentDocs, исключения FILE/PATH/REG). Оба безопасны:
`Default=False`, цели — классический клинеровский мусор (кэш
обновлений, CBS/DISM-логи, WER, дампы). Откройте их в редакторе,
чтобы увидеть поля формы заполненными реальными значениями; «Анализ»
покажет настоящий объём.

## Структура записи

```ini
[Название записи *]
Section=Custom
Default=False
Warning=Текст предупреждения, показывается при выборе
DetectFile=%ProgramFiles%\MyApp
FileKey1=%LocalAppData%\MyApp\Cache|*.*|RECURSE
FileKey2=%AppData%\MyApp\logs|*.log
RegKey1=HKCU\Software\MyApp\Cache
ExcludeKey1=FILE|%LocalAppData%\MyApp\Cache|keep.me
```

| Ключ | Назначение |
|---|---|
| `[Имя *]` | Заголовок секции — имя записи в списке. Хвост ` *` по традиции winapp2 (парсер его срезает). |
| `Section=` | Категория в списке (Browser, System, Custom…). Необязательно. |
| `Default=` | `True` — отмечена по умолчанию при загрузке; `False` — нет. Для своих правил лучше `False`: выбор осознанный. |
| `Warning=` | Текст, который клинер показывает при работе с записью. Необязательно. |
| `DetectN=` / `Detect=` | Запись «установлена», если существует ключ реестра (`HKCU\Software\Foo`, `HKLM\SOFTWARE\Foo`). |
| `DetectFileN=` / `DetectFile=` | Запись «установлена», если существует файл/папка (`%ProgramFiles%\Foo`). |
| `DetectOS=` | Гейт по версии Windows: `10` — минимум, `6.1|10` — диапазон «мин|макс». Необязательно. |
| `SpecialDetect=` | Готовые шорткаты: `DET_CHROME`, `DET_FIREFOX`, `DET_IE`, `DET_THUNDERBIRD`, `DET_OPERA`, `DET_EDGE`, `DET_WINSTORE`. |
| `FileKeyN=` | Файлы/папки на удаление (см. ниже). |
| `RegKeyN=` | Ключи реестра на удаление (см. ниже). |
| `ExcludeKeyN=` | Исключения внутри записи (см. ниже). |

Нумерация ключей — `FileKey1`, `FileKey2`, … — порядок и пропуски в
номерах не важны.

**Запись без Detect/DetectFile** считается всегда установленной и
показывается в списке — для Custom-файлов это легально (permissive
режим). В основных базах такая запись была бы отброшена.

**Запись без FileKey/RegKey** ничего не удалит — после Analyze у неё
пустой результат.

## FileKey — файлы и папки

```
FileKeyN=<путь>|<маски>[|RECURSE|REMOVESELF|UNSAFE]
```

- `<путь>` — каталог или файл. Поддерживаются `%Переменные%` и
  wildcard-сегменты внутри пути (`...\Profile *\Cache`).
- `<маски>` — маска файлов (`*.*`, `*.log`), несколько через `;`
  (`*.tmp;*.bak`). Без масок — удаляется сам указанный объект.
- `RECURSE` — искать по маске во всех подкаталогах.
- `REMOVESELF` — после чистки удалить и сам каталог, если опустел.
- `UNSAFE` — снимает **только для этого ключа** фильтр запускаемых
  файлов: по широкой маске (`*.*`) под удаление подпадут и `.exe`,
  `.bat`, `.ps1` и т.п. Остальные защиты работают всегда: защищённые
  пути, ExcludeKey, проверка занятых файлов. Флаг — явное решение
  автора правила, используйте осознанно.

Флаги идут после пути **в любом порядке**: `path|UNSAFE|*.exe|RECURSE`
эквивалентно `path|*.exe|RECURSE|UNSAFE`. Первый токен, не являющийся
флагом, становится маской.

Примеры:

```ini
FileKey1=%LocalAppData%\App\Cache|*.*|RECURSE      ; всё в Cache и ниже
FileKey2=%AppData%\App\logs|*.log                  ; только *.log, без подкаталогов
FileKey3=%ProgramFiles%\App\crash.dmp              ; один файл
FileKey4=%Temp%\AppTemp|*.*|REMOVESELF             ; содержимое + сама папка
```

## RegKey — реестр

```
RegKeyN=<путь ветки>[|<имя значения>]
```

- Без имени значения — удаляется вся ветка с подключами:
  `RegKey1=HKCU\Software\MyApp\Cache`
- С именем — удаляется только значение:
  `RegKey2=HKCU\Software\MyApp|LastSession`

Hive-префиксы: `HKCU`, `HKLM`, `HKCR`, `HKU` (длинные
`HKEY_CURRENT_USER\...` тоже понимаются). 32-битный view проверяется
там, где WOW64 реально разделяет ключ (`HKLM\SOFTWARE`, `HKCR`).

## ExcludeKey — исключения

```
ExcludeKeyN=<FILE|PATH|REG>|<путь>[|<маска>]
```

| Тип | Что исключает |
|---|---|
| `FILE` | Файл/маску внутри удаляемого каталога: `ExcludeKey1=FILE|%AppData%\App|settings.ini` |
| `PATH` | Весь подкаталог: `ExcludeKey2=PATH|%AppData%\App\Important` |
| `REG` | Ключ/значение реестра: `ExcludeKey3=REG|HKCU\Software\App\Keep` |

## Переменные окружения

Внутри путей работают `%Имя%` — свои плюс любые системные env-vars:

| Переменная | Раскрывается в |
|---|---|
| `%AppData%` | Roaming-профиль пользователя |
| `%LocalAppData%` | Local-профиль |
| `%LocalLowAppData%` | LocalLow-профиль |
| `%ProgramFiles%` | Program Files (64-бит; x86-вариант проверяется автоматически) |
| `%ProgramFiles(x86)%`, `%ProgramFilesX86%` | Program Files (x86) |
| `%ProgramData%`, `%CommonAppData%` | ProgramData |
| `%UserProfile%` | Профиль пользователя |
| `%Documents%`, `%Desktop%`, `%Music%`, `%Pictures%`, `%Videos%` | Папки пользователя |
| `%SystemRoot%`, `%WinDir%` | Каталог Windows |
| `%System%`, `%SystemX86%` | System32 / SysWOW64 |
| `%Temp%`, `%Tmp%` | Временная папка |
| `%SystemDrive%` | Диск системы (`C:` → нормализуется в `C:\`) |

### Свои переменные — `Custom\_vars.ini`

Файл `Custom\_vars.ini` с секцией `[Vars]` регистрирует свои
`%Имя%`-псевдонимы — чтобы правила оставались переносимыми между
машинами (`%TC%\Cache` вместо `C:\TC\Cache`). Имена совпадающие со
встроенными переопределяют их — только для своих правил:

```ini
[Vars]
TC=C:\TotalCmd
Tools=D:\Tools
```

`%TC%` после этого работает в FileKey/DetectFile наравне с системными.

## Безопасность

- Свои правила проходят те же гейты, что и встроенные: защищённые пути
  `cs.safety` (Windows, корни дисков, системные ветки реестра) отсекаются
  и в Analyze, и повторно в Clean — сломать систему записью из Custom
  заметно сложнее.
- Удаление прямое, **без корзины** — проверяйте результат Analyze
  перед нажатием «Очистить».
- `REMOVESELF` без маски и `RECURSE` на широких путях (`%UserProfile%`)
  — самые опасные комбинации. Пишите путь максимально узко.
- Проверить правило без риска: создайте файл, нажмите «Анализ» в
  клинере, посмотрите, что попало в план — удаляться ещё ничего не будет.
